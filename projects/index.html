    DearAlpha: Quantitative Alpha Factor Mining Framework for WorldQuant Brain DearAlpha：面向 WorldQuant Brain 的量化 Alpha 因子挖掘框架
    Huang Yuchang 黄宇场
    Apr 2026 – Sep 2026 2026.04 – 2026.09
    Python WorldQuant Brain API Optuna TPE Multi-LLM
    Context: Brute-force template enumeration on WorldQuant Brain quickly hits API rate limits on large search spaces and cannot discover new structures, whereas asking an LLM to write full alphas directly often leads to syntax errors or overfitted expressions lacking economic logic. Actions: Built 6 mining modes around an "AI generates raw signals, code enumerates and verifies, humans make final decisions" workflow: (1) integrated multi-backend LLMs (OpenRouter / Anthropic / Ollama) rotating across 10 economic themes (momentum, value, volatility, etc.) to propose template-free raw factor expressions; (2) implemented a 3-stage progressive pipeline (1st-order time-series ops → 2nd-order cross-sectional grouping → 3rd-order trade-event filtering) keeping Top-N expressions per field, designed two-pass layered pruning (shortlisting Top-K fields with representative windows → full window grid), and used Optuna TPE Bayesian sampling to tune window and decay parameters; (3) added checkpoint resumption (progress.json) and pre-submission checks (Sharpe, Fitness, Turnover, Prod Correlation) for rate-limited batch submission. Results: Two-pass pruning cut redundant backtest simulations by ~50% compared with full Cartesian enumeration, automating the local loop from LLM hypothesis generation and batch parameter tuning to quality-gated submission. 背景：在 WorldQuant Brain 挖量化因子时，传统模板笛卡尔积穷举在搜索空间变大后极易卡死在平台回测限流上且写不出新结构，而直接让大模型写完整因子又常因语法错误或缺乏经济学逻辑过拟合，需要一套把「大模型出思路」和「代码批量搜索调参」结合起来的自动化工具。动作：按「AI 生成裸信号、代码枚举验证、人做最终判断」开发 6 种挖掘模式：（1）接入多后端 LLM（OpenRouter / Anthropic / Ollama），按动量、价值、波动率等 10 类经济学主题轮询生成不受固定模板限制的原始因子表达式；（2）把经典挖掘流程做成「一阶时序算子 → 二阶截面分组 → 三阶交易事件过滤」三级流水线，各阶按 Sharpe 与 Fitness 阈值过滤且同字段仅留 Top-N 进入下一阶；针对大字段集设计「少量代表性窗口粗筛 Top-K 字段 → 完整窗口网格」两阶段剪枝，并用 Optuna TPE 贝叶斯采样对窗口长度和 Decay 等连续参数做自动精调；（3）实现基于进度快照（progress.json）的断点续跑，并在提交前自动校验 Sharpe、Fitness、Turnover 与线上相关性（Prod Correlation）以批量限速提交。结果：两阶段剪枝相比全量笛卡尔积穷举减少了约 50% 的无效回测请求；打通从 LLM 提因子假设、多模式批量回测调参、中断自动续跑到质量门控提交的本地自动化闭环。

    DevFlow Engine: AI-Driven Requirement-to-Delivery Workflow Engine DevFlow Engine：AI 驱动的研发需求交付流程引擎
    Huang Yuchang 黄宇场
    Apr 2026 – May 2026 2026.04 – 2026.05
    Python LangGraph Python AST Tree-sitter lark-cli WebSocket
    Context: Unconstrained single-agent coding often modifies files blindly without understanding repository structure, while natural-language requirements in Feishu groups usually require manual PRD writing, technical design, and coding across disconnected tools. Built a "fixed pipeline controls flow, specialized agents execute, humans approve key checkpoints" delivery engine (2026 Feishu AI Campus Challenge AI Rising Star & Final Interview Fast-Track). Actions: (1) Used LangGraph to split delivery into 6 dedicated Agent stages (intake → solution design → code generation → test generation & execution → code review → delivery packaging); connected lark-cli WebSocket to listen to Feishu group messages, auto-create PRD docs and interactive cards, and enforce 2 human approval checkpoints (after solution design and after code review, supporting Approve/Reject and checkpoint recovery); (2) extracted symbol definitions, references, and call chains via Python ast and tree-sitter (Python / JS / TS) before coding so agents understand existing code structure within workspace-bounded file tools, and added a read-only code review stage that automatically feeds blocking issues back to the coding node for one self-repair pass. Results: Enabled an end-to-end loop where sending a single requirement message in a Feishu group drives requirement clarification, solution approval, coding, unit testing, self-review repair, and merge-ready delivery packaging, preventing blind file edits and keeping code changes controllable. 背景：用纯自主 Coding Agent 开发复杂需求时，模型容易在不了解代码库结构的情况下乱改文件、一步错步步错；而飞书群里提的自然语言需求平时要靠人手写 PRD、拆技术方案再去改代码，中间链路很割裂。为此开发「固定流水线控流程、专门 Agent 干活、关键节点由人拍板」的需求交付引擎（获 2026 飞书 AI 校园挑战赛 AI 新星证书及直通终面奖励）。动作：（1）基于 LangGraph 将研发流程拆成「需求分析 → 方案设计 → 代码生成 → 测试生成与执行 → 代码评审 → 交付打包」6 个独立 Agent 阶段；通过 lark-cli WebSocket 长连接监听飞书群消息，自动生成 PRD 文档与交互卡片，并在「方案设计后」与「代码评审后」设置 2 处飞书人工审批检查点（支持 Approve / Reject 与断点恢复）；（2）在写代码前先用 Python ast 和 tree-sitter（支持 Python / JS / TS）提取代码库符号定义、引用关系与调用链，让方案与代码 Agent 先看懂现有代码结构再动手，并限制文件工具仅能在工作区目录内读写；在代码评审阶段采用只读审查，发现阻塞性 Bug 时自动把评审意见塞回代码生成节点重跑一次自修复。结果：实现「在飞书群发一条需求消息，即可跑完需求澄清、方案审批、写代码跑单测、代码自审修复到产出合并交付包」的完整闭环；通过 AST 索引和两处人工审批卡点，解决了单 Agent 乱改代码和过程不可控的问题。
